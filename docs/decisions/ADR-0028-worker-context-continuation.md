# ADR-0028: Workers hand over at 300k and a fresh copy continues the step

Date: 2026-08-23

Status: accepted. The brain handover it builds on is gone (ADR-0041); the worker continuation below stays.

## Context

A worker agent that runs long fills its context window. Nothing bounded it: quality dropped as the harness compacted the transcript, cost rose because every turn resent the full context, and a session that died at the limit left nothing behind but the files it happened to write. The brain already solved this for itself (ADR-0024, `tangent brain handover`), but `tangent goal handover` means "my step is done": it advances the pipeline. There was no way to hand the same step to a fresh copy of the same agent.

The design (`~/.tangent/trees/otto/tangent/design-worker-context-handover.md`, solution `impl-worker-context-handover.md`) set the yardstick: no forced kill and no lost facts, written memory crosses sessions, nothing happens below the threshold, the trigger comes from outside the agent, the same verbs and machinery as every other handover, pipelines and reviews stay intact, degrade safely per harness, testable without live harnesses.

## Decision

- **The threshold is one absolute constant.** `CONTEXT_HANDOVER_TOKENS` (default 300000, env `TANGENT_CONTEXT_HANDOVER_TOKENS`) in `packages/agent-shell/app/server.mjs`, beside `BRAIN_WAIT_NOTICE_MS`. A model whose context window is at or under the threshold (Opus 4.6 at 200k) is exempt: it just uses its full window, today's behavior. There is no percentage and no per-model table.
- **Tangent reads the fill from the pane it already captures.** `parseContextFill` (`pane-state.mjs`) adds a `context` pattern per harness family to `PANE_SIGNATURES`: claude's statusline `8% (78k/1000k)`, pi's footer `6.8%/1.0M`. Codex has no pattern yet, its fixture shows no fill; a harness without a pattern reads as `null`, which is always inert (never reminds, never shows, never changes reminder state). An inverted reading (used > window) also reads as `null`.
- **Tangent reminds; the step prompt teaches the verb.** The reminder is the trigger, never the agent's own judgment alone: `reconcileContextHandovers` (called from `reconcileGoals` after `reconcileBrains`, sharing its 10-second throttle) queues one message at the threshold with the exact command, and one stronger repeat once carried context is a tenth further. Each level fires at most once per session; state is keyed by session name on the step or the solo continuation record, so a compaction dip never re-arms a level that already fired, and a server restart re-reminds at most once. `pipelineStepPrompt`'s `## When you finish` and `goalPrompt`'s `## How to work` each carry one added sentence naming the threshold and the flagged command, so a worker can hand over early on its own judgment even without a reminder.
- **The verb is a flag on the existing one.** `tangent goal handover --continue "<facts>"` (packages/agent-shell/src/cli). Plain `handover` still means "step done": it advances the pipeline. `--continue` means "this step is not done; a fresh copy of me continues it." The reminder always prints the whole flagged command, so a worker never composes it from memory.
- **The swap contract**, `continueWorkerSession` in `server.mjs`, and the order is load-bearing:
  1. Resolve the caller: a running pipeline step, a solo Goal session, or (neither) a session that already swapped away, refused 409 naming the live session, or refused 404.
  2. Derive the fresh name (`continuationSessionName` in `context-handover.mjs`): strip the current session's own generation suffix, then the smallest `<stem>--g<n>` not already live.
  3. **Write the record first.** A pipeline step's `continuations` list gains `{ session, next, facts, at, fill }` and `step.session` moves to the fresh name; a solo session's `goal-continuation.v1` record (new module `continuation-record.mjs`, one file per Goal under `~/.tangent/agent-shell/continuations/<area>/<slug>.json`) gets the same. Facts are on disk before any spawn: a crash between spawn and prime loses nothing.
  4. Retarget the message queue to the fresh name, dropping any pending context-reminder (a fresh session earns its own if it also fills); a brain answer in flight survives the move.
  5. Spawn the fresh session, primed with the rebuilt prompt (`pipelineStepPrompt` or `goalPrompt`) plus every non-failed continuation's facts in order (`continuationSection`).
  6. **Kill the old session only once the new one confirms.** `spawnGoalSession` gained `onPrimed`, threaded through `primeGoalSession`'s existing `onTyped` hook into `armSession`; it fires `true` only after `tickArmedSessions` confirms the whole prompt arrived (not merely typed), `false` on a session death or a failure before that. On `true`: kill the old tmux session directly (never through `endPipelineForSession`, which would end the whole run and tell the brain a step died), notify the brain with the old and new names and the carried fill, and, on the step or Goal's third non-failed continuation, add a notice that it is probably oversized. On `false`: kill the new session, restore the step or record to the old session, retarget the queue back, rebind the Goal file to the old session, and type the error into the old session so it keeps working the step. A restart between spawn and prime loses the `onPrimed` callback (armed prompts persist on disk without callbacks); both sessions then stay alive, the record already points at the new one, and the old session is refused by name on its next command.
- **Both handover verbs refuse a swapped-away caller.** `swappedAwayNaming` scans every pipeline step's and solo record's `continuations` for the caller's name; a plain `handover` or a `--continue` from a dead-but-not-yet-killed session cannot complete or re-continue the step out from under the live one.
- **The grace window also covers the newest continuation.** `stepStartedWithinGrace` (`pipeline-record.mjs`) took only `step.startedAt`; a continuation moves `step.session` to a tmux session that may not exist yet in a sessions snapshot while `startedAt` stays old. It now takes the later of `startedAt` and the last continuation's `at` (NaN-safe finite maximum), so a reconcile pass inside the swap window cannot mark the live step stopped (`goal-tangent-never-marks-a-live-step-stopped`).
- **The desk shows the fill only at the threshold.** `GET /api/sessions` carries `contextHandoverTokens` and each session's/step's `context`; the row shows the carried tokens (`310k`) next to the state pill only once it reaches the threshold, nothing below it.

## Consequences

- New pure modules: `pane-state.mjs` gains `parseContextFill`; new `context-handover.mjs` (`reminderDue`, `contextReminderText`, `contextRepeatText`, `continuationSessionName`, `continuationSection`) and `continuation-record.mjs` (mirrors `pipeline-record.mjs`).
- `POST /api/goals/handover` branches on `body.continue === true`; the CLI gains one option, no new command family.
- `deliverAgentMessage` gained `entry.render`: a queued message can rebuild its text at delivery time, so a reminder's fill number is the one Tangent sees when it actually lands, not when it was queued.
- Nothing changes for a session below the threshold, for the plain handover verb, for `completePipelineStep`, for review structure, or for the brain's own self-handover.
- Testable without a live harness: `context-handover.test.mjs` and `continuation-record.test.mjs` pin the pure rules; `context-continuation.test.mjs` proves the swap, its refusals, and the reminder pass end to end with `AGENT_SHELL_TEST_NO_LAUNCH=1` and real tmux sessions (never a real harness). The one thing no unit test covers is a harness actually confirming a fresh prompt and the resulting kill; that is proven live, once, against a real worker under a lowered `TANGENT_CONTEXT_HANDOVER_TOKENS`.

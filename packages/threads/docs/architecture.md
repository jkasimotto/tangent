# @tangent/threads Architecture

Delegated-thread sweep, registry, and attach.

Rules:
- Do not depend on Usage (full package), Rollup, or Eval. Only @tangent/usage-index-sqlite for session telemetry (the vertical-dependency rule extends from "rollup/eval -> usage" to "rollup/eval/threads -> usage").
- Reach the vault by path convention only (same as the tangent skill), never as a code dependency.
- Use @tangent/repo for path helpers (worktree path normalization) and @tangent/agent-runtime for process execution (the haiku runner, terminal-notifier).

Pipeline (src/core/sweep.ts):

Pi Code is the default dispatch runtime but is not yet a Usage provider. Registrations marked `runtime: "pi"` therefore use `TmuxSessionStateReader`: Pi runs non-interactively in a tmux pane configured with `remain-on-exit`, and `pane_dead` provides a deterministic working-to-finishing transition while retaining output for attach. Mid-flight question detection remains Claude-only in this v1 runtime adapter.
1. `scanVault` (src/core/vault-scan.ts) walks the vault once: `thread-*.md` files (excluding `shared/`), `overview.md` "## On me" backlog items, and per-node note recency from `YYYY-MM-DD-*.md` filenames. Parsing itself (src/core/thread-parser.ts, src/core/overview-parser.ts) is pure; only the file walk is IO.
2. For each thread with a sidecar registry entry, `SessionStateReader` (src/core/types.ts) resolves live session telemetry. It is a narrow injectable interface so the pure derivation logic and its tests never touch the Usage SQLite index directly. The default implementation (src/core/sqlite-session-state.ts) queries `@tangent/usage-index-sqlite`'s `openUsageFromSqlite({ scope: "all" })`. A registry entry with no session id yet (dispatch cannot always observe it) is resolved by matching the most recently active session whose cwd/repo fields equal the registered worktree path, gated by the entry's `registeredAt` (minus a 2-minute slack) so a long-lived, reused worktree cannot latch onto a session that predates this dispatch, e.g. a recur thread misattributing Julian's own interactive session in the same directory; the resolved id is persisted back into the registry so later sweeps query by id directly. Each thread's optional wake condition (a `Wake on <date>` or `Wake when <branch> is merged into <target> in <repo>` body line) is also evaluated here (src/core/wake.ts) against the clock and local git state (`merge-base --is-ancestor`, no fetch); any other prose stays opaque and keeps v1 behavior, listed as parked until a human unparks it.
3. `deriveThreadStates` (src/core/derive.ts) is a pure function implementing the design spec's state table exactly (working / blocked-on-you / finishing / ready-for-you / needs-you / parked / done), given already-resolved facts, session state, landed evidence, validation evidence, and the wake-condition verdict. An ended session is only `finishing`; `ready-for-you` requires explicit staging evidence. Registered branch/base pairs are checked with local `merge-base --is-ancestor` before deadlines, so landed work produces a truthful close prompt instead of a stale deadline nag. No model involvement.
4. `WhyLineRunner` (src/core/haiku.ts) asks a cheap model (haiku by default) for why-lines and check-in drafts, given the already-derived states as input; it cannot change a state, and any runner failure (missing binary, timeout, bad JSON) falls back to templated why-lines built from owner/deadline/cadence facts during derivation. Output is filtered to known slugs only before use.
5. `buildThreadsView` (src/core/render.ts) resolves each open thread's final why-line into a persistable view; `renderThreadsMarkdown` renders that view as `threads.md`: a `NEEDS YOU` strip on top, then the vault's node tree with every open thread and unowned item under its node (label chains collapsed, state icons per line). The view is persisted in the sidecar so `tangent threads list <subtree>` re-renders a filtered tree (`filterViewBySubtree`/`nodeMatchesSubtree`) without re-sweeping. `sidecar.ts` computes fresh counts and the notification-dedup transition and writes the sidecar. Both outputs are written atomically (tmp file + rename, src/core/atomic-write.ts) only after every prior step succeeds, so a scan or derivation error leaves both files untouched. Fanned-out dispatch threads sharing a `Batch: <name>` body line sort together within their node (by batch, then slug) and get their why-line prefixed `[<name>]`, so a batch reads as one group instead of scattering across individual urgency order.
6. Notifications fire only for threads newly entering blocked-on-you, needs-you, or ready-for-you since the previous sweep (deduped via the sidecar's `notified` map); each carries identity, reason, and resolving verb. `renderThreadsStatusBadge` applies the same compact summons shape and exposes sweeps older than one hour as stale.
7. `updateSharedNodes` (src/core/sweep.ts) regenerates the "Delegated threads" section of every shared node's `shared/state-of-play.md`: for each node with both a `shared/` directory and at least one non-done thread, `renderStateOfPlaySection` (src/core/state-of-play.ts) renders one line per thread, most-urgent-first, and `updateSharedStateOfPlay` conservatively splices it between `<!-- tangent-threads:begin -->`/`:end` markers, refusing to write (and logging the marker counts) when the file's marker state is ambiguous rather than guessing which pair is real. The default `GitSharedStateWriter` commits a written change locally with `commitPath` (targeting only `state-of-play.md`, never a whole-tree `git add -A`, since `shared/` is a durable human-owned repo) when the shared directory is its own git repo, and never pushes; one node's failure never fails the sweep or any other node's update.

Lifecycle (src/core/lifecycle.ts): `markValidationReady` records the reviewed surface and verdict in the registry; the next sweep deterministically transitions the thread from finishing to ready-for-you. `cleanupThread` acts only on `created` resource lists, reports every `reused` resource as skipped, uses non-forced worktree removal, and proves each branch merged into its registered base before `git branch -d`.

Refer to ../../../docs/architecture/package-boundaries.md and ../../../docs/architecture/dependency-graph.md for monorepo boundaries.

Attach (src/core/attach.ts): `openAttach` opens a registered thread's tmux session in a new full-screen iTerm window. Every step exists because the naive version failed silently: absolute tmux path (iTerm profile commands run without the user's shell PATH), pre-flight `has-session`, idempotent two-pane layout (worker left, `nvim .` right in the worktree), AppleScript fed to osascript via stdin (no shell quoting) that sizes the window to the screen, and a post-launch poll of `tmux list-clients` requiring a NEW client tty before reporting success. Plain `tmux attach`, never `-CC` control mode, which leaves a stray control window and depends on iTerm tmux-integration prefs. The process runner, filesystem probe, and sleep are injectable, so tests never spawn tmux or osascript.

Milestones (src/core/milestone.ts, src/core/clipboard.ts): parse-and-render only, no state of its own. The milestone file lives in the vault and is human-curated; `loadNodeMilestone` picks the nearest-future due date; three renders (terminal project view, Slack mrkdwn text, clipboard HTML) share one timeline builder so countdown math cannot drift between surfaces; `setClipboardRich` sets «class HTML» plus «class utf8» flavors through osascript with an injectable runner. Nothing here writes to the vault or posts anywhere: updating checkboxes stays a human/agent edit, and Slack posting stays a human paste.
